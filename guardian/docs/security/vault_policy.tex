\begin{abstract}
\noindent This document defines the access control policies, path-scoped secret isolation, and automated 24-hour asymmetric key rotation protocol governing inter-service communication between the Guardian, Digital Twin, and City Brain layers.
\end{abstract}

\vspace{0.3cm}

\section{Scope and Requirements}
The specification enforces mutual cryptographic isolation and automated daily rollover of RSA-4096 communication keys between the \texttt{guardian}, \texttt{twin}, and \texttt{brain} services. All communications require asymmetric signing and encryption, preventing unauthorized lateral movement.

\section{Identities and AppRole Policies}
Four distinct AppRole identities govern the cryptographic perimeter:
\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \textbf{guardian-app, twin-app, brain-app:} Scoped microservice identities possessing read-only access restricted strictly to their own cryptographic paths.
  \item \textbf{rotator:} Dedicated administrative AppRole used by the daily rotation daemon. Possesses create/update rights on \texttt{secret/data/comm/*} and metadata read rights, but cannot read plaintext key values.
\end{itemize}
Services authenticate using AppRole credentials to acquire short-lived leased tokens ($\text{TTL} = 15$\,min, $\text{max\_TTL} = 1$\,h). Policies reside in \texttt{vault/policies/} and are applied idempotently via \texttt{vault/setup\_policies.py}.

\section{Key Ownership and Mutual Isolation}
Each unidirectional channel between layers utilizes an independent RSA-4096 key pair owned by the sender:
\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \texttt{secret/comm/OWNER/PEER/private} is readable by \textbf{OWNER only}.
  \item \texttt{secret/comm/OWNER/PEER/public} is readable by \textbf{PEER only}.
\end{itemize}

\noindent A default-deny policy applies to all other paths. Public keys are integrity-protected by Vault (TLS in transit, KV versioning, audit trail) and are never accepted from untrusted channels.

\section{Automated 24-Hour Key Rotation Protocol}
The key rotation daemon (\texttt{vault/rotate\_keys.py}) executes daily at 02:00 via a systemd timer. For each of the six communication channels, the workflow executes:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
  \item Generates a fresh 4096-bit RSA key pair.
  \item Writes the new public key (creating a new KV version with a unique Key ID \texttt{kid}).
  \item Writes the new private key stamped with \texttt{active\_after = now + 1h}.
\end{enumerate}

\subsection{Safe Transition Window (Zero Downtime)}
\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \textbf{Dual Verification Window:} Peer receivers query \texttt{vault\_keys.verification\_keys}, accepting both Version $N$ (current) and Version $N-1$ (previous).
  \item \textbf{Delayed Signing Activation:} The sender continues signing with Version $N-1$ until the 1-hour delay expires (\texttt{vault\_keys.signing\_key}), ensuring all peers have cached Version $N$ before first use.
  \item \textbf{Version Retention:} KV v2 retains 5 historical versions before automated pruning.
\end{itemize}

\section{Revocation and Incident Response}
\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \textbf{Compromised Token:} Revoke immediately via \texttt{vault token revoke <token>}.
  \item \textbf{Compromised Secret ID:} Destroy via \texttt{vault write auth/approle/role/ROLE/secret-id/destroy secret\_id=ID} and re-issue.
  \item \textbf{Service Compromise:} Revoke all service tokens, trigger emergency execution of \texttt{rotate\_keys.py}, and purge compromised key versions via \texttt{vault kv destroy -versions=N}.
\end{itemize}

\end{lstlisting}
